# calmgap-tokyo

**東京都は次にカームダウン・クールダウンスペースをどこに設置すべきか。**
オープンデータだけで設置優先度を算出し、根拠つきで提言する行政・事業者向けの分析ツール。

都知事杯オープンデータ・ハッカソン 提出作品。

---

## これは何か / 何ではないか

感覚過敏（発達障害・精神障害・PTSD 等）のある人にとって、都市は音・光・匂い・混雑の刺激で
過負荷になりやすい。過負荷時に一時退避できるカームダウン・クールダウンスペースの整備は、
障害者差別解消法改正（2024 年〜、合理的配慮の民間義務化）を追い風に進みつつある。

しかし整備は施設単位の個別事例として進んでおり、
**都全体を対象に需給を俯瞰して配置優先度を分析した公開資料は確認できていない**
（港区役所・都立中央図書館・一部の駅など、個別の設置事例は公表されている）。
本プロジェクトは「需要が高く、環境負荷も高く、逃げ場がない場所」をオープンデータから算出し、
**次に検討すべき区画をランキングして根拠付きで示す**。

**示すのは 250m の区画であって、特定の施設ではない。**
このモデルには施設の適性を測る構成要素が一つも無く、建物の余剰空間も運営体制も
測っていない。9,507 区画を、人が話し合う価値のある十数区画まで絞り込む道具であり、
どこに置くかを決める道具ではない（`docs/methodology.md` 7.0）。

| | |
|---|---|
| ✅ 作るもの | オープンデータから算出する**設置優先度スコア**の地図と、上位地区ごとの**「なぜここか」根拠カード**（そのまま予算会議に出せる資料） |
| 🚫 作らないもの | 個人が「今どこへ行くか」を選ぶ口コミ／ディスカバリーアプリ、リアルタイム経路案内、ユーザー投稿機能、**特定の施設への設置提言** |

利用者は当事者本人ではなく、**配置を決める行政・鉄道事業者・施設運営者**。
使う瞬間は「次の一箇所をどこに作るか決めるとき」。

| | |
|---|---|
| 対象 | **東京 23 区** / JIS X 0410 5 次メッシュ（250m）**9,507 区画** |
| データ | **実データ 10/10 レイヤー**（模擬データなし） |
| 供給側 | 公共施設 **1,541 件**（23 区すべての公共施設一覧 + 国土数値情報 P14 の児童館） |
| 既存施設で到達不可 | **1,058 区画（11.1%）**。うち区内で優先度が中位以上は 148 件 |
| 公開 | https://calmgap-tokyo.hiroaki-kuwabara.workers.dev |

**到達不可率を区どうしで比べてはいけない。** 皇居・羽田空港・埋立地・河川敷の
面積比でほぼ決まるため（江東区 38.7% / 世田谷区 0.8%）。
比べるなら「区内で優先度が中位以上の到達不可区画」を使う
（[`docs/issues.md`](docs/issues.md) A9）。

## 分析モデル

```
設置優先度 = 需要スコア × 負荷スコア
```

足し算ではなく **掛け算**。人がいて **かつ** 過負荷、の両方が揃った場所だけを立てるため。
静かな住宅地に当事者が住んでいても公共の退避場所は要らないし、
うるさくても誰も通らない場所にも要らない。足し算だと、
どちらか一方が極端に高いだけの場所が上位に紛れ込む。

需要を **「住んでいる場所」ではなく「通わざるを得なくて、かつ過負荷になりやすい場所」** で
定義し直しているのが本作の肝。カームダウンスペースは寝る場所ではなく
overwhelm される場所に置くものだから。

| 側 | レイヤー |
|---|---|
| 需要 | 障害福祉サービス事業所（定員 × 種別重み）／特別支援学校（規模）／駅乗降規模／精神科・心療内科 |
| 負荷 | 用途地域／自動車騒音（幹線道路の道路端）／混雑（昼間人口）／緑・公園被覆（**減点**） |

**「実データ 10/10 レイヤー」の 10 と、この表の 8 は数え方が違う。**
データの層は 10 で、**そのうちスコアに入るのが 8**。入らない 2 層は
**既存の公共施設**（徒歩圏 700m に 1 件も無い区画を「到達不可」と判定する。
優先度には一切入らないので、この判定だけはスライダーで動かない）と
**区界**（メッシュを張る範囲と区名）である。
画面はこの対応を `meta.layer_roles` から出す（`etl/config.py` の `SUPPORT_LAYERS`）。

**用途地域を感覚負荷の予測器に転用している**のが技術的な独自性。
用途地域は「その土地が法的にどこまで騒がしくなり得るか」の上限を定めた規制であり、
実測点が疎な感覚負荷を面として推定するのに使える。
詳細と重みの根拠は [`docs/methodology.md`](docs/methodology.md)。
作業を中断・再開するときは [`docs/status.md`](docs/status.md) が起点。

## 動かす

### 1. データを生成する

```bash
pip install geopandas pandas numpy shapely pyproj requests
python -m etl.build            # 模擬データ（ネットワーク不要）
python -m etl.build --report   # 上位メッシュと構成要素間の相関も表示
```

### 2. 地図を開く

```bash
cd web
npm install
npm run dev                    # http://localhost:5173
```

### 3. 検証する

```bash
python -m etl.selftest         # 地理計算とスコア正規化の不変条件
node tools/parity_check.mjs    # Python と TypeScript のスコアが一致するか
```

## ⚠️ 現在のデータ状態

`python -m etl.build --live` は **実データ 10/10 レイヤー**で動く（模擬データなし）。
`data/processed/` に正規化済みのものが入っている。

**引数なしの `python -m etl.build` は模擬データで動作する。**
その場合、地図上の数値・施設名はすべて架空であり実際の提言として引用できない
（画面上部に警告バナーが出る）。

実データであることと数値が確からしいことは別で、出典そのものの弱さは残る。
未解決の偏りと不透明さは [`docs/issues.md`](docs/issues.md) に一覧してある。
とくに騒音は幹線道路の道路端しか測っておらず、23 区の内側にある測定点は
6 年分（令和元〜6年度）の和集合で 965 点だが、**区ごとに 17〜65 点と 3.8 倍の開き**がある。しかも**苦情が出た道路を測る要請限度が混ざっており**、それは文京区・渋谷区では 5 年分でも 0 点である。混雑は昼間人口ではなく従業者数で代替している。
特別支援学校の規模は 45 校中 42 校が実在籍者数だが（国立 3 校は公表が無く既定値）、
**規模を実数にしてもこの層を外すと上位 10 件が全部入れ替わる**——
上位の顔ぶれがこの層 1 枚に強く依存している。
詳細は [`docs/status.md`](docs/status.md) の「まだ本物でないもの」。

開発環境から各オープンデータ配信サーバへの接続が組織のネットワークポリシーで
遮断されているため、取得はローカル環境で行う必要がある。
そこで ETL・スコアリング・地図 UI を実データの取得可否から切り離せるよう、
`etl/fixtures.py` が空間的に一貫した模擬データを生成する構成にしてある。

- 座標のアンカー（駅・公園の位置）だけは実際の地理を使っている。
  ここを架空にすると「上位メッシュが実際にキツい場所と一致するか」という
  サニティチェックの予行演習ができなくなるため。
- 乗降人員・定員・騒音値・施設名はすべて生成値。全レコードが
  `source="SYNTHETIC FIXTURE"` を持ち、施設名には「模擬」を冠してある。
- 模擬モードのビルドでは画面上部に警告バナーが出る（`meta.json` の `synthetic` で制御）。

### 実データへの切り替え（1レイヤーずつ）

全レイヤーがそろうまで待つ必要はない。**落とせた分だけ実データに差し替わる。**

```bash
python -m etl.fetch --inspect data/raw/P14-21_13_GML
python -m etl.fetch --normalize p14 data/raw/P14-21_13.geojson
python -m etl.build --live
```

**`--inspect` はフォルダでもファイルでも受ける。** 展開したフォルダを渡せば、
中のデータファイルを再帰的に列挙して件数と列名を出す。まず何が入っているかを
一望できないと手の付けようがないため。

**`--normalize` にフォルダを渡せるのは `a29` と `s12` だけ**（前者は都市計画区域ごとに
数十ファイルへ分割配布されるため結合し、後者は文字コード違いの同一データが
2 部入っているため片方だけを読む）。他はファイルを指定すること。
CSV のレイヤー（`noise` `facilities` `estat-pop`）は CSV 専用で、Excel なら先に書き出す。

区ごとに分かれたファイルは**並べて渡せる**。まとめて正規化し、
同一施設（同名かつ 100m 以内）を 1 件に寄せてから書き出す。

```bash
python -m etl.fetch --normalize facilities ~/Downloads/渋谷区.csv ~/Downloads/世田谷区.csv --append  # 23 区分は docs/handoff-hosts.md
```

`--normalize` の種別: `n03` `p14` `p14-hosts` `wamnet` `p29` `p04` `a29` `s12` `p13`
`noise` `facilities` `estat-pop`

### ひとつのレイヤーを複数の出典が書く

`hosts` は `p14-hosts`（児童館）と `facilities`（区の公共施設一覧）が、
`welfare` は `p14` と `wamnet` が書く。あとから流した方が既存を丸ごと
置き換えるため、**児童館 154 件を消したことに気付かないまま
「既存施設では到達不可」が増える**という壊れ方をしていた。

既存の出典が消える場合は書かずに止まり、どちらか選ばせる。

- `--append` — 既存と統合する（同一施設は名称と位置で 1 件に寄せる）
- `--replace` — 既存を捨てて入れ替える（WAM NET で P14 を置き換える場合など）

同じ出典を入れ直すだけなら止まらない。そのとき既存の古い行は捨てて
新しい行を採る（逆だったため、正規化を直して入れ直しても出力が変わらなかった）。

**`n03`（行政区域）を最初に入れること。** これが入るまで研究領域は暫定の矩形で、
対象区の外まで含んでしまう。

ビルド時にどのレイヤーが実データかが表示され、模擬が残っていれば
画面のバナーにも「実データ 9/10 レイヤー」「模擬: population」と出る。
**1 レイヤーでも模擬が残っている限り、数値は提言として引用できない。**

現在は 10 レイヤーすべてが実データで、`data/processed/` に正規化済みのものが入っている
（需要 14,118 事業所 / 駅 617 / 特別支援学校 45 / 精神科 1,548 /
用途地域 7,002 / 騒音 1,058 点 / 公園 3,835 / 混雑 4,221 メッシュ / ホスト施設 1,541）。
各レイヤーの入手手順は [`docs/status.md`](docs/status.md) の「投入済みレイヤーの入手元」。

### ビルド後に git pull が止まる場合

`web/public/data/` の中身は ETL の生成物だが、**追跡対象にしてある**。
クローンしただけで地図が開けることを優先したため（審査でリポジトリを
そのまま開く人がいる）。その代わり、ローカルで `python -m etl.build` を
実行した後は差分が出て `git pull` が止まる。

生成物なので捨ててよい。pull 後に再生成すれば同じものが戻る。

```bash
git checkout -- web/public/data/
git pull
python -m etl.build --live
```

---

`etl/fetch.py` の取得処理は **実サーバに対して未検証**。
列名マッピング（`COLUMN_MAP`）は各データの仕様書に基づく想定値なので、
実ファイルを 1 度落とした時点で `--inspect` で必ず突き合わせること。
オープンデータは年度で列名も配布形態も変わる。

### 列名が違っていたら黙って進まない

A29 用途地域で一度やった: 仕様書から推測した列名が外れ、**全件 NaN のまま
既定値が全メッシュに乗り、それでもビルドもテストも成功と表示された**。
負荷スコアの主軸が消えていることに、出力を見ても気付けなかった。

同じ構造は列名を決め打ちする全レイヤーにあったので、投入前に揃えてある。
数値に影響する列は、

1. 列名で見つからなければ **列の中身** から探し、見つけたら何を選んだか表示する
2. それでも特定できなければ、**各列の実際の値を添えて例外で止まる**
3. 絞り込みの結果が 0 件になったら止まる（0 件のレイヤーは実データとして
   数えられたまま、その構成要素を消してしまう）

止まるのは、たとえば診療科目の列を取り違えたとき（全医療機関が精神科として
需要に乗る）、公共施設一覧の名称列を取り違えたとき（ホスト候補が 0 件になり
「既存施設では到達不可」が過大に出る）。表示にしか使わない列
（地点名・区名など）は欠けても進むが、警告は必ず出る。

その列が**本当に収録されていない年度**のときだけ、既定値での代用を明示的に許す:

```bash
python -m etl.fetch --normalize p29 <ファイル> --assume-missing
```

使えるのは P29 の児童生徒数と WAM NET の定員だけで、
使えば「規模による重み付けは効かない」と警告が出る。

## 重みはスライダーで動かせる

「その重み付けは恣意的では?」は当然の批判で、それに文章で反論するのは弱い。
そこで **重みをブラウザ側のスライダーに出し、審査員自身が動かせるようにした**。
ETL が配信するのは正規化済みの各構成要素までで、最終スコアはブラウザで決まる。
上位が重みを変えても大きく動かないなら、それはモデルが頑健だということ。

立場の違いをそのまま示すプリセットも用意してある
（聴覚過敏を重視 / 通所先・通学先の近く / 大規模駅の周辺）。

さらに地図の表示を **設置優先度 / 需要のみ / 負荷のみ** で切り替えられる。
「需要 × 負荷」と主張する以上、掛ける前の 2 つを別々に見せられなければ検証しようがない。
需要のみ・負荷のみで濃かった場所が掛け算で消えることが、
足し算ではなく掛け算にした理由の実演になる。

根拠カードには正規化スコアではなく **実数** を載せている
（1 位の例:「徒歩圏の事業所は 44 件・定員 394 人、精神科・心療内科 6 件、
最寄り駅 亀戸（52m・乗降 13.6 万人/日）、用途地域は商業地域、推定騒音 67.2dB、
昼間の従業者 2,216 人、緑被覆 0%。徒歩圏の区の公共施設は 6 件で最寄りは 200m」）。
「需要 0.99」では予算会議の資料にならないため。

### 重みを変えても結論は変わるのか

スライダーを用意しても、審査員が実際に動かすとは限らない。
そこで **動かした結果を数値で出しておく**（`python -m etl.build --live --sensitivity`）。

- 重みを **±30% ランダムに動かしたとき**（500回試行）、上位10区画に残るのは
  **66.6%**（最悪 **0%**）。上位50区画なら 83.4%。順位の変動は中央値 7 位。
  **「上位 10 件」を固定の答えとして提示してはいけない。**
- 立場の違う **4 プリセット全てで上位20件に入る区画は 0 件**。
  「重みの選び方に関係なく上位に来る場所がある」とは言えない。
- **1 レイヤーを外すと上位10件が全部入れ替わることがある。** 最も効くのは
  特別支援学校（外すと重なり **0%**）、次いで用途地域（20%）・事業所と緑被覆（40%）。
- **重み以外の固定値 76 個**（仮定員・種別重み・帯域・用途地域の負荷値・α/β 等）を
  同時に ±30% 動かすと **46.7%**（最悪 0%）。最も効くのは帯域（65.3%）で、
  その重さは丸ごと**特別支援学校 1 層**から来る（単独 63.7%）。
  **いちばん効かないのは騒音の内挿（99%）**——2026-08-04 に測定点を
  383 → 1,058 点へ増やして、内挿の設定への依存が下がった。

**この作品の順位は、特別支援学校というレイヤー 1 枚に強く依存している。**
規模を仮定値から実データにしたときは提言 8 件のうち 4 件が入れ替わり、
その帯域を 1,200m から 800m へ直したときは提言が 8 件 → 11 件になった
（**いずれも提言が「地区」単位だった頃の数え方**。2026-08-03 に単位を
区画へ戻したので、いまの提言は順位表そのものである）。
帯域を直したのは根拠が持たなかったためで（`docs/issues.md` A4）、
**その結果ここに並ぶ安定性の数字はどれも悪化している。**
都合の良い側だけを引用しないための記録として、両方を残してある。

**原因は 23 区に 45 校しかないこと**で、重みでも帯域でも解けない。
面に撒く以上「学校の徒歩圏に入っているか」というゲートになり、
どこに線を引くかが恩恵を受ける区画を決めてしまう。
**手法の限界であって実装の不具合ではないため、直さず明記する方針を採った**
（需要側から外すのが構造的な解で、これは今後の課題）。

**一方、順位に依存しない出力がひとつある。**
**「徒歩圏 700m に区の公共施設が 1 件も無い区画」1,058 件（11.1%）**は、
重みもスコアも帯域も通っていない——最寄りの公共施設までの距離だけで決まる。
**この作品でいちばん頑健なのはこちらで、順位は「その中でどこから見るか」を
探すための道具**だと考えている。

模擬データの頃は駅レイヤーを外すと上位が半分入れ替わる一方、
需要側の事業所を外しても 100% 変わらなかった。「上位は駅と用途地域だけで
決まっている」状態で、渋谷が上位に来る結論は部分的に自己成就していた。
自分たちのモデルに不利なこの結果も隠さず出している。
詳細は [`docs/methodology.md`](docs/methodology.md) の 8.2.5。

---

この設計上、**同じ数式が Python と TypeScript に 2 つ存在する**。
両者がズレると初期表示とスライダー既定値で色が食い違うため、
`tools/parity_check.mjs` が全メッシュで一致を検証している。
`tools/facility_parity.mjs` は**「徒歩圏の件数」と「地図に光る点の数」の一致**を
全 9,507 区画 × 4 層で検証する（画面が「60 件」と書いた隣で 59 点しか
光らない、という食い違いを防ぐ）。

## 構成

```
calmgap-tokyo/
├─ etl/
```

## 出力データ

`python -m etl.build` が `web/public/data/` へ書き出す。

| ファイル | 内容 |
|---|---|
| `mesh.geojson` | メッシュ形状 + 正規化済み構成要素（`n_*`）+ 既定重みでのスコア |
| `cards.json` | 上位メッシュの根拠カード（要因の内訳と日本語の根拠文） |
| `proposals.json` | 提言リスト（＝優先度の順位表）。**単位は区画**で、地区でも施設でもない |
| `hosts.geojson` / `demand_points.geojson` | 供給側・需要側の点データ |
| `noise_points.geojson` | 自動車騒音の測定地点（1,058 点・位置と dB と年度と**調査名**）。**施設ではない**ので需要側の点とは別ファイルにしてある。騒音の値がどこの測定に由来するのか、どこが測られていないのかを地図で見せるためのもの |
| `meta.json` | 構成要素定義・出典・生成条件・模擬データか否か |

`cards.json` と `proposals.json` は**既定重みでの静的な書き出し**で、資料添付用。
画面上の提言リストは現在のスライダー値から毎回組み直される。

## ライセンスと出典

- 公的オープンデータは概ね CC BY 相当（出典表示が必要）。出典は `meta.json` と
  画面内「算出方法とデータ出典」に列挙し、`etl/config.py` の `SOURCES` を単一の情報源とする。
- ベースマップは[国土地理院 淡色地図タイル](https://maps.gsi.go.jp/development/ichiran.html)。
- **民間人流データを組み込む場合は ODPT チャレンジの特定利用条件に縛られる**ため、
  作品の公開範囲と整合するか必ず確認すること（現時点では未組み込み）。
- 精神障害者保健福祉手帳の交付状況は**集計統計のみ**を扱い、
  個人特定に繋がる粒度では表示しない。区単位の全体係数としてのみ使用する設計。
