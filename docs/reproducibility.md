# 更新性 — どこまで自動で、どこから人手か

**「他の自治体でも回せるのか」に答えるための 1 枚。**

この作品は方法を提案するものなので、**その方法が他の手で回るかどうか**が
主張の一部になる。いまの正直な答えはこうである。

> **回せる設計にはなっている。ただし、回したことはまだ 1 度も無い。**
> 対象を変えるのに書き換えるのは `etl/config.py` の数行だが、
> **供給側データの収集だけは自動化していない**（できていないのではなく、
> 出典の側がそういう形で配られていない）。

`docs/operation-idea.md` と同じで、**ここに書いてあるのは事実であって
提案ではない。** 未実施のことは未実施と書く。

---

## 1. 4 つの段のうち、人手が要るのは 1 段だけ

```
  ① 入手        生ファイルを data/raw へ置く          ← 人手
  ② 正規化      python -m etl.fetch --normalize ...   ← 自動（列は中身で同定）
  ③ 集計・配信  python -m etl.build --live            ← 完全自動
  ④ 検査        selftest / parity / doc_numbers 他    ← 完全自動（CI）
```

②③④ はコマンド 1 本で、判断が要る場所が無い。**①だけが人手である。**

### なぜ ① を自動化していないか

**できないからではなく、出典の側が年度ごとに配布の形を変えるからである。**

- 国土数値情報は**年度ごとに URL が変わる**（`N03-2024` と `N03-v3_1` は
  別ページで、後者は最新が 2023 年版。`docs/issues.md` の出典点検を参照）
- ZIP の中の階層とファイル名も年度で変わる（S12 は `UTF-8/` と `Shift-JIS/` に
  同一データが 2 部入っている年がある）
- 東京都のオープンデータカタログは bot 対策の裏にあり、HTML を機械的に辿れない
  （CKAN の API 側は素通し）

`python -m etl.fetch --check` は**登録した全出典への到達性だけ**を確かめる。
そこから先、どのリンクがその年度の本体かは人が見る。

**URL を決め打ちで自動ダウンロードする作りにはしていない。**
一度そうすると、年度が変わった瞬間に**古いデータで静かに通る**ビルドになる。
止まるほうがよい。

### いちばん重いのは供給側

**区の公共施設一覧は 23 区で約 30 本を毎回すべて並べて渡す。**
同じ出典ラベルなので 1 本だけ渡すと他区が消える。実際のコマンドは
[`docs/handoff-hosts.md`](handoff-hosts.md) にある。

区ごとに:

- 統合一覧を持たない区がある（港・江戸川・中野）
- KML の区がある（足立）
- xlsx の区がある（北・大田）
- **名称の列名が「列1」の区がある**（江東。表計算の既定値に化けている）
- **座標が無い区がある**（千代田は 230 行すべて空、品川は列自体が無い）
  → `etl/geocode.py` が住所から当てる（外部 API を使わず、国土交通省の
  位置参照情報だけを使う。理由は同ファイルの docstring）

**これは技術の問題ではなく、公開のされ方の問題である。**
1 区が様式を変えるたびに、こちらは `--inspect` で列を見ることになる。

## 3. 列が変わったときに何が起きるか

**黙って通らない。** 数値に影響する列は `require_column` を通す。

1. 列名で見つかっても、**中身が合わなければ採らない**
2. 列名で見つからなければ**中身から探す**（何を選んだか表示する）
3. それでも特定できなければ、**各列の実際の値を添えて例外で止まる**
4. 絞り込みの結果が 0 件でも止まる

一度、仕様書から推測した列名が外れて**全件 NaN のまま既定値が全メッシュに乗り、
ビルドもテストも成功と表示された**ことがある。この作りはその事故から来ている
（`CLAUDE.md`「壊れ方の型 — 列名の決め打ち」）。

出典リンクも「開けること」ではなく「**読み込んだファイル名がその先にあること**」
まで検査する（`tools/link_check.py`）。

## 4. 他の地域へ移すとき何を変えるか

**書き換えるのは `etl/config.py` の 3 か所。**

| 何 | 定数 | いまの値 |
|---|---|---|
| 対象地域 | `TARGET_WARDS` | 23 区の区名 |
| メッシュ次数 | `MESH_LEVEL` | 5（250m） |
| 重みとプリセット | `ALL_COMPONENTS` / `PRESETS` | 作者の初期値 |

**コードは触らない。** 帯域・半径・正規化の方式も全部 `config.py` にある。

ただし正直に書くと、**移した先で必ず要る作業が 2 つ残る**:

1. **供給側データの収集**（その自治体の公共施設一覧。上記のとおり様式が違う）
2. **重みの決め直し**——8 つの重みに外部の根拠は無い（作者が 0.5〜1.0 の幅で
   置いた初期値）。だから動かせるようにしてあり、動かすと何がどれだけ変わるかを
   画面の感度分析に出している

**「設定を変えれば動く」とだけ書くのは正確ではない。** 動くが、
その土地の人が重みを決め直さないと、出てくるのは東京の価値判断である。

## 5. まだやっていないこと

- **他地域で実際に回したことが無い。** 対象は 23 区のみで、多摩・島しょは未対応
  （供給側データを 26 市町村分そろえる必要がある）
- **①の自動化。** 出典側の配布形態が安定していないので、当面は人手
- **CI での定期実行。** いまの CI は検査だけで、データの再取得はしない

## 6. いま CI が毎回確かめていること

データを入れ替えなくても、**壊れたら止まる**ようにはなっている。

```bash
python -m etl.selftest        # 71 件。不変条件と「間違いが黙って通らないこと」
node tools/parity_check.mjs   # Python と TypeScript のスコア一致（全 9,507 区画）
node tools/facility_parity.mjs # 数えた件数と地図に光る点の一致（全区画 × 6 群）
python tools/doc_numbers.py   # 文書の現況値が配信データと合っているか
python tools/link_check.py    # 出典リンクが「そのデータのある場所」を指しているか
```

**これらは内部整合しか見ていない。** モデルが現実を当てている証拠にはならないので、
既存のカームダウンスペースとの外部照合を別に行っている（`docs/status.md`）。
