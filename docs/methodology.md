# 算出方法

`calmgap-tokyo` の設置優先度スコアの定義、重みの根拠、既知の限界。
審査における「データ活用」「技術力」の説明を兼ねる。

---

## 1. 全体の流れ

```
オープンデータ（点・線・面・統計表）
    ↓ etl/fetch.py        取得と共通スキーマへの正規化
    ↓ etl/aggregate.py    標準地域メッシュへの集計
    ↓ etl/score.py        パーセンタイル正規化 → 需要×負荷
    ↓ etl/hosts.py        ホスト施設の割当と根拠カード生成
web/public/data/*.json → ブラウザで重みを再計算
```

---

## 2. なぜ標準地域メッシュか

独自の格子ではなく **JIS X 0410 標準地域メッシュ**（`etl/mesh.py`）を採用している。

理由は結合性。e-Stat の地域メッシュ統計（国勢調査・昼間人口）は
メッシュコードをキーに持つため、標準メッシュを使えば **空間補間なしで直接結合できる**。
独自格子にすると、最も信頼できる人口統計を最初に歪めることになる。

MVP は **5 次メッシュ（250m 四方、東京付近で実測 約 232m × 283m）** を既定とする。
`--level 4`（500m）でも動く。

粗い統計（3 次 = 1km）を細かいメッシュへ結合する際は、
値を子メッシュ数で **等分** する（`aggregate.join_by_mesh_code`）。
人口は密度量であり、1km メッシュの値をそのまま 250m メッシュへ複製すると 16 倍に膨らむ。
総量が保存されることは `etl/selftest.py` で検証している。

## 3. 点・線・面をメッシュに載せる

オープンデータは形式がバラバラで、そのままでは同じ土俵に乗らない。
`etl/aggregate.py` が 4 通りの変換を持つ。距離・面積計算はすべて
平面直角座標系第 IX 系（EPSG:6677）で行う。緯度経度のまま距離を測ると
東京では経度方向が約 18% 過大に出る。

### 3.1 点 → メッシュ（距離減衰カーネル）

事業所・学校・駅などに使う。
単純な「メッシュ内に落ちた点を数える」集計は採らない。
250m メッシュに対して徒歩圏は 800m あり、隣接メッシュの事業所も
そのメッシュの需要を確かに生んでいる。境界のどちら側に立っているかで
スコアが不連続に変わるのは、提言の根拠として弱い。

```
w(d) = exp(-0.5 × (d / bandwidth)²)     d > 2×bandwidth では 0
```

帯域は施設種別で変える。影響の及ぶ範囲が違うため。

| レイヤー | 帯域 | 理由 |
|---|---|---|
| 障害福祉サービス事業所 | 800m | 徒歩約 10 分。感覚過敏当事者は移動そのものが負荷になるため、一般的な生活圏（1km）よりやや短く取る |
| 特別支援学校 | 1200m | 広域から通学し、送迎車両の往来も周辺に広がる |
| 駅 | 600m | 雑踏・アナウンス・改札の過負荷は駅前で急激に減衰する |
| 精神科・心療内科 | 800m | 通院は徒歩圏が基本 |

### 3.2 点 → メッシュ（逆距離加重 / IDW）

騒音に使う。自動車騒音の要請限度測定は **幹線道路沿いの点でしか測っていない**。
点しか無いものを面に変換するのが本作の技術的主張のひとつ。

```
v(mesh) = Σ wᵢvᵢ / Σ wᵢ,    wᵢ = 1 / (dᵢ + 50m)²,    dᵢ > 1500m では 0
```

分母の平滑化項（50m）は、測定点直上での 0 除算と極端なスパイクを避けるため。

**1500m 以内に測定点が無いメッシュは 0 ではなく欠測（NaN）とし、中央値で補完する。**
0 で埋めると「最も静かな場所」として最上位に評価されてしまう。
補完したセル数はビルド時にログへ出す。

### 3.3 面 → メッシュ（面積加重平均）

用途地域に使う。1 メッシュが複数の用途地域区分に跨る場合、
重心が乗った 1 区分で代表させると境界メッシュの評価を誤るため、
重なり面積で加重平均する。

### 3.4 面 → メッシュ（被覆率）

公園・緑地に使う。メッシュ面積に占める割合 0〜1。
重なり合うポリゴン（公園の多重登録）で 100% を超えないよう、先に融合してから交差を取る。

## 4. 正規化

各レイヤーは単位が違う。定員（人）・騒音（dB）・被覆率（比）を足すことに
意味を持たせるには、いったん共通の物差しに載せ替える必要がある。
本作は **対象地域内でのパーセンタイル順位** を使い、0〜1 に正規化する。

絶対値ではなく順位を使うのは、外れ値（巨大ターミナル 1 駅）に
スコア全体が支配されるのを防ぐため。

### 4.1 「0」の扱いを 2 通りに分ける

ここが正規化の設計上の要点。

| 種別 | 対象 | 扱い |
|---|---|---|
| **不在** (`zero_is_absence=True`) | 事業所・学校・駅・クリニック・混雑・緑被覆 | 0 は「存在しない」。厳密に 0 とし、正の値だけを (0, 1] に順位配分する |
| **連続量** (`zero_is_absence=False`) | 用途地域スコア・騒音 | 全体を [0, 1] に順位配分する |

区別しないと、事業所が 1 件も無いメッシュ群が「ゼロの塊の平均順位」として
0.3 程度の需要を持ってしまい、**住宅地を落とすという掛け算モデルの狙いが崩れる**。

同値には平均順位を与える。

## 5. 合成

```
需要スコア = percentile( Σ wᵢ × signᵢ × nᵢ )    over 需要レイヤー   … 不在扱い
負荷スコア = percentile( Σ wⱼ × signⱼ × nⱼ )    over 負荷レイヤー   … 連続量扱い
設置優先度 = 需要スコア^α × 負荷スコア^β         （既定 α = β = 1）
```

重み付き和をもう一度パーセンタイル正規化して 0〜1 に戻すのは、
重みの合計が変わってもスケールが一定になり、スライダー操作で色が飛ばないようにするため。
相対比較のツールなので、絶対値には意味を持たせない。

**掛け算にする理由**: 人がいて **かつ** 過負荷、の両方が揃った場所だけを立てるため。
需要が 0 のメッシュは優先度も厳密に 0 になる（`etl/selftest.py` で検証）。

**片側の重みを全て 0 にした場合**、その側は「評価しない」＝中立の 1.0 として
掛け算から外す。0 のままだと全メッシュの優先度が 0 になり地図が消える。

## 6. 重みの根拠

### 6.1 需要レイヤー

| レイヤー | 既定重み | 根拠 |
|---|---|---|
| 障害福祉サービス事業所（定員重み） | 1.0 | 就労移行・就労継続 A/B・生活介護・放課後等デイ等の定員は、その徒歩圏を日常的に往復せざるを得ない当事者の実数に最も近い代理変数 |
| 駅乗降規模 | 0.9 | 「通わざるを得ない過負荷な場所」の中核。その地点を通過せざるを得ない人の総量 |
| 特別支援学校（規模重み） | 0.8 | 通学は選択の余地がない移動。児童生徒本人と送迎者が同一時間帯に同一地点へ集中する |
| 精神科・心療内科 | 0.5 | 受診当日は体調が不安定なことが多く、退避先の必要性が最も高い移動のひとつ。ただし他レイヤーより点数が少なく代表性が弱いため低め |

事業所は **定員 × 種別重み** で評価する（`etl/schema.py`）。
種別重みは「定員 1 人あたり、どれだけの過負荷な外出を生むか」で決める。
カームダウンスペースは寝る場所ではなく overwhelm される場所に置くもの、
という前提をここで実装している。

| 種別 | 重み | 理由 |
|---|---|---|
| 放課後等デイサービス・児童発達支援 | 1.00 | 児童。送迎者と併せ 1 定員あたりの往来が最も多い |
| 就労移行支援 | 0.95 | 通所が原則で、就活等の外出も伴う |
| 就労継続支援 A/B 型・生活介護 | 0.85–0.90 | 日中の定期通所 |
| 短期入所 | 0.35 | 滞在型 |
| 共同生活援助（GH）・施設入所支援 | 0.15–0.25 | 居住系。日中はそこに居ない |
| 居宅介護・重度訪問介護・同行援護 | 0.10 | 訪問系。事業所所在地に人は集まらない |

### 6.2 負荷レイヤー

| レイヤー | 既定重み | 根拠 |
|---|---|---|
| 用途地域 | 1.0 | 後述 |
| 自動車・鉄道騒音 | 0.9 | 聴覚過敏の直接要因。ただし測定点が疎で内挿の不確実性があるため 1.0 未満 |
| 混雑（昼間人口） | 0.8 | 人的密度そのものが視覚・聴覚・触覚の同時多重刺激を生む |
| 緑・公園被覆 | 0.6（**減点**） | 既に安らげる空間が担保されている場所は新規整備の優先度を下げてよい |

### 6.3 用途地域を感覚負荷の予測器に転用する

本作の独自性の中心。用途地域は都市計画の規制情報であって騒音データではないが、
**「その土地が法的にどこまで騒がしくなり得るか」の上限** を定めている。
騒音の実測点は幹線道路沿いにしか無い一方、用途地域は全域を面で覆う。
そこで用途地域を 0.0〜1.0 の負荷スコアへ写像する。

序列の根拠は建築基準法別表第二の用途制限：

| 用途地域 | 負荷 | 理由 |
|---|---|---|
| 第一種低層住居専用 | 0.05 | 住宅と小規模併用のみ。カラオケ・遊技場・工場を一切許さない |
| 第二種低層住居専用 | 0.12 | |
| 第一種／第二種中高層住居専用 | 0.20 / 0.28 | |
| 第一種住居 | 0.38 | |
| 第二種住居 | 0.50 | **カラオケボックス・パチンコが解禁される。ここに段差を置く** |
| 準住居 | 0.60 | 幹線道路沿いが前提 |
| 近隣商業 | 0.74 | |
| **商業** | **1.00** | 用途無制限に近く、深夜営業・大型ビジョン・繁華街雑踏が集中する |
| 準工業 / 工業 / 工業専用 | 0.78 / 0.85 / 0.90 | 騒音源としては大きいが歩行者の滞留は少ない。負荷自体は高く評価し、「人がいない」ことは需要スコア側が掛け算で打ち消す（役割分担） |
| 田園住居 | 0.08 | |

用途地域が指定されていない区域は 0.30 を既定値とする。

## 7. ホスト施設の割当

ヒートマップは行政の意思決定にそのまま使えない。
上位メッシュに **実在する公共施設** を割り当て、「この施設に置け」まで言い切る。

最寄りを機械的に選ぶのではなく、施設種別の優先順位を距離より上位のキーにする。
150m 先の駅より 400m 先の図書館を選ぶ、という判断を入れている。

| 種別 | 優先度 | 理由 |
|---|---|---|
| 図書館 | 1 | 静穏であることが既に運営方針に含まれており、一室を転用する合意形成の難易度が最も低い |
| 区民センター・出張所 | 2 | 個室・相談室を持つことが多い |
| 文化施設・児童館 | 3 | |
| 公園管理施設 | 4 | |
| 駅 | 5 | 鉄道事業者との別途調整が要る |

**半径 700m 以内に候補が無いメッシュは失敗ではなく、それ自体が提言**。
「既存の公共ストックでは到達できない＝新規整備または民間施設との連携が要る」区画として
赤く表示し、その件数を画面上部の見出し数値に出している。

提言リストは施設単位に束ねる。ひとつの図書館が隣接する複数の高優先度メッシュを
まとめて受け持つことは多く、メッシュを羅列すると同じ施設が何度も出てきて提言として読めない。
束ねた件数がそのまま「1 箇所の整備で何メッシュ分に効くか」＝費用対効果の説明になる。

### 7.1 根拠カードには正規化値ではなく実数を載せる

スコアは順位に正規化された相対値なので、それ単体では提言文にならない。
「需要 0.94」ではなく **「徒歩圏に障害福祉サービス事業所 4 件・定員 77 人、
最寄りの渋谷駅は乗降 687,169 人/日、用途地域は商業地域、推定騒音 71.3dB、緑被覆 0%」**
と書けて初めて予算会議の資料になる。

そのため ETL は表示専用の実数列（接頭辞 `f_`）を別に計算して配信する。
スコア計算には一切使わない。

| 列 | 内容 | 算出 |
|---|---|---|
| `f_welfare_n` / `f_welfare_cap` | 徒歩圏の事業所数・定員合計 | 半径 800m の**素朴な件数**（距離減衰なし） |
| `f_school_n` / `f_clinic_n` | 特別支援学校数・精神科等の件数 | 同上 |
| `f_station_name` / `f_station_riders` / `f_station_dist` | 最寄り駅の名称・乗降人員・距離 | 最近傍（1500m 以内） |
| `f_zoning_name` | 面積最大の用途地域区分名 | 面積最大クラス |
| `f_noise_db` / `f_green_pct` | 推定騒音・緑被覆率 | 生値 |

スコアには距離減衰カーネルを使うが、カードの数字は**素朴な件数**を使う。
「重み付き 3.7 施設」では説明できないため。用途地域も、負荷スコアは面積加重平均
（連続値）で計算する一方、カードには面積最大の区分名を出す。
平均値 0.82 では審査員にも行政にも伝わらない。

## 7.5 表示モード（需要 / 負荷 / 掛け算）

「需要 × 負荷」と主張する以上、掛ける前の 2 つを別々に見せられないと検証しようがない。
地図には 3 つの表示モードを用意している。

| モード | 見えるもの |
|---|---|
| 設置優先度 | 需要 × 負荷。両方が揃った場所だけが濃くなる |
| 需要のみ | 通わざるを得ない人の量だけ。住宅地や郊外の通所拠点も濃く出る |
| 負荷のみ | 過負荷になり得る量だけ。人のいない工業地帯も濃く出る |

需要のみ／負荷のみで濃かった場所が掛け算で消えることが、
**足し算ではなく掛け算にした理由の実演** そのものになる。

## 8. モデルの妥当性検証

### 8.1 サニティチェック

上位メッシュが、当事者や報道が知る「実際にキツい場所」（大ターミナル周辺等）と
一致するかを目視する。

**実データ 4/9 レイヤー時点の結果（渋谷区＋世田谷区・5次メッシュ 1,116 区画）**

優先度上位 10 メッシュはすべて渋谷駅から 583m 以内に収まり、
最上位クラスタは駅から 79〜320m に位置する。

| メッシュ | 中心 | 渋谷駅からの距離 |
|---|---|---|
| 5339358633 | (139.7016, 35.6573) | 79m |
| 5339359611 | (139.7016, 35.6594) | 153m |
| 5339358634 | (139.7047, 35.6573) | 291m |
| 5339358631 | (139.7016, 35.6552) | 311m |
| 5339359612 | (139.7047, 35.6594) | 319m |

重要なのは **実データ 2 層が独立に同じ場所を指している** こと。

| レイヤー | 上位メッシュでの正規化値 | 出所 |
|---|---|---|
| 障害福祉サービス事業所 | 0.97〜0.99 | 実データ（P14） |
| 用途地域 | 0.98〜0.995 | 実データ（A29） |
| 駅乗降規模 | 0.97〜1.00 | 模擬 |
| 昼間人口 | 0.98〜0.99 | 模擬 |

駅乗降規模は模擬データで渋谷を最大に設定してあるため、それ単独では自己成就的である。
しかし需要側の実データ（事業所分布）と負荷側の実データ（用途地域）が、
駅データとは無関係に同じ地点を指している。モデルの妥当性はこの一致に支えられている。

なお `n_sped_school` は上位メッシュで全て 0 だが、特別支援学校は模擬データであり
郊外寄りに配置してあるため。実データ（P29）投入後に再確認が要る。

### 8.2 構成要素間の相関

`python -m etl.build --report` が相関行列を出す。
**0.9 を超えるペアは、1 つの現象を二重計上している疑いがある。**

**実データ 4/9 レイヤー時点**：最大は 駅乗降規模 × 昼間人口 = **0.769**。
0.9 を下回っており、二重計上はない。

模擬データのみの段階では 用途地域 × 昼間人口 が 0.86 に達していたが、
用途地域を実データに差し替えると **0.421 へ低下**した。
高い相関はフィクスチャが両者を同一の「都市らしさ」場から生成していた人工物であり、
実データでは独立性が保たれていることが確認できた。

> ⚠️ 現在最大の 駅乗降規模 × 昼間人口 = 0.769 も、**両方とも模擬データ**であり
> 同じ場から生成されている。ODPT と e-Stat の実データ投入後に再確認すること。

### 8.2.5 感度分析 — 重みへの依存度を測る

「その重み付けは恣意的では?」への回答をスライダーだけに委ねると、
審査員が実際に動かしてくれるかどうかに賭けることになる。
そこで **動かした結果がどうなるかをあらかじめ数値で出す**（`etl/sensitivity.py`）。

```bash
python -m etl.build --live --sensitivity
```

#### ランダム摂動（全レイヤーの重みを同時に ±30%、500 回試行）

| 対象 | 平均で残った割合 | 最悪 |
|---|---|---|
| 上位 10 区画 | **96.1%** | 80.0% |
| 上位 20 区画 | 97.8% | 90.0% |
| 上位 50 区画 | 98.4% | 92.0% |

順位の変動は中央値 1 位、90%点 3 位。
**重みを ±30% 適当にずらしても、上位の顔ぶれはほぼ変わらない。**

#### プリセット比較（立場の違う 4 通り）

既定・聴覚過敏重視・通所通学重視・ターミナル重視の 4 プリセット全てで
上位 20 件に入った区画は **16 件（80%）**。
重みの選び方に関係なく上位に来る場所がある、という提言に直結する結果。

#### Leave-one-out（各レイヤーを外したときの上位 10 件の重なり）

| 外したレイヤー | 重なり |
|---|---|
| **駅乗降規模** | **50%** |
| 用途地域 | 80% |
| 自動車・鉄道騒音 | 90% |
| 混雑（昼間人口） | 90% |
| 障害福祉サービス事業所 / 特別支援学校 / 精神科 / 緑被覆 | 100% |

> ⚠️ **最も結果を左右しているのは駅乗降規模であり、これは現在まだ模擬データである。**
> 模擬データでは渋谷駅の規模を最大に設定してあるため、
> このレイヤーへの依存は「渋谷が上位に来る」という結論を部分的に自己成就させている。
> 8.1 のサニティチェックは実データ 2 層（事業所・用途地域）が独立に同じ地点を
> 指していることに支えられているが、**駅データを実データへ差し替えたうえで
> この分析を再実行するまで、依存度の評価は暫定である。**
>
> 逆に、需要側の実データである障害福祉サービス事業所を外しても上位 10 件が
> 100% 保たれるのは、現在の上位が駅と用途地域で決まっていることを意味する。
> 需要レイヤーの寄与を強めるには WAM NET による件数・定員の回復が要る。

### 8.3 既存カームダウンスペースとの照合（Phase 2）

中央集約されたオープンデータは存在せず、手作業の名寄せが必要なため MVP では扱わない。
役割は「モデル妥当性の検証」と「東京には N 個しかない」という提示に限定する。

高需要メッシュに寄っていればモデルが妥当、ズレていれば
「現在の配置がニーズと合っていない」という提言そのものになる。
**どちらに転んでも発見になる**設計。

## 8.4 研究領域は行政界から導出する

国土数値情報 N03 を投入するまで、研究領域は手書きの矩形
`(139.5500, 35.5900, 139.7350, 35.6900)` だった。これには 2 つの誤りがあった。

1. **対象2区の外まで含んでいた。** 港区・目黒区・品川区の一部が入り、
   実際に港区の施設が提言リストに出た。
   「渋谷区と世田谷区が対象」と言いながら港区の施設を提言するのは提言物として成立しない。
2. **渋谷区の北端が切れていた。** 渋谷区の北限は緯度 35.6920 だが、矩形の上限は 35.6900。

N03 から対象区のポリゴンを取り出し、その外接矩形をメッシュの範囲に、
ポリゴン自体をクリップに使うことで両方とも解消した。
5次メッシュは 2,832 セル → **1,116 セル**（対象2区の実面積）になった。

### 入力データだけ余白付きで拾う

メッシュは区界で厳密に切るが、**入力データの絞り込みには区界の外側 2km の余白**を取る
（`config.CLIP_BUFFER_M`）。区界ちょうどで切ると、境界のすぐ外にある事業所や駅が落ちる。
需要は 800m の距離減衰カーネルで周囲へ及ぶため、境界外の施設も区内メッシュの需要を
確かに生んでいる。ここを切ると縁のメッシュだけ需要が不自然に低く出る（エッジ効果）。

### 区境をまたぐ設置候補は消さずに明示する

対象区内のメッシュに対し、最寄りのホスト施設が隣接区にあることは珍しくない。
当事者にとって区境は意味を持たないので割当自体は残すが、
提言先の自治体が変わるため `host_ward` を持ち回り、
「ただし港区の施設であり、対象区の所管外。区境をまたぐ連携が前提になる」と明示する。

## 8.5 実データで判明した P14 の制約（重要）

国土数値情報 P14 福祉施設（東京都・15,838件）を実際に投入して分かったこと。
**当初の設計前提が 2 つ崩れた。**

### 定員フィールドが存在しない

`P14_009` は設置主体コード（0〜5）、`P14_010` は位置正確度コードであり、定員ではない。
需要を「定員 × 種別重み」で測るという本モデルの前提が、P14 単独では満たせない。
暫定措置として種別ごとの仮定員（`schema.ASSUMED_CAPACITY`）を当てているが、
**WAM NET の実定員が入るまでこの層は推定値**である。

### 障害福祉と高齢者介護が分類コードで分離できない

| 小分類 | 件数 | 障害系の語を含む名称 | 高齢系の語を含む名称 | どちらも無し |
|---|---|---|---|---|
| 991100「障害者福祉施設等」 | 6,065 | 986 | 971 | 4,135 |
| 991200「相談支援・訪問系等」 | 1,754 | 483 | 250 | 1,150 |
| 991007「グループホーム」 | 937 | **1** | **214** | 723 |

991007 は名称を見る限り実質すべて認知症対応型GH・小規模多機能であり、
障害者グループホームではない。中分類（`P14_006`）でも分離できない。

高齢者介護施設の混入は需要マップを別物にしてしまうため、
**取りこぼしても混入させない**方針を採った（`schema.P14_SUBCLASS` の `scope`）。

| scope | 扱い |
|---|---|
| `include` | コードだけで障害福祉と断定できる。無条件で採用 |
| `name_gated` | 障害/高齢が混在。名称が障害系のときだけ採用 |
| `exclude` | 高齢者介護・保育・医療。常に除外。未知コードもここへ倒す |

結果：15,838件 → 障害福祉と判定 1,552件（うちコードで断定 86件、名称で判定 1,466件）。
研究領域内 219件。

**これは過小計上である。** 命名慣行に従わない事業所は落ちている。
件数の正確さは WAM NET（サービス種別と定員を持つ）で回復する。
したがって **WAM NET は代替候補ではなく必須ソース** に位置づけが変わった。

### 副産物：児童館をホスト施設として確保できた

P14 の `051301` は児童館で、東京都に 587 件ある。
区市町村ごとにバラバラな公共施設一覧を集める前に、提言の割当先をそろえられる。
実データを見て初めて分かったこと。

## 8.6 実データで判明した A29 の制約

### 用途地域コードは A29_004（推測は外れた）

仕様書から `A29_005` と推測していたが、実データでは **`A29_004`** だった。
そのまま走らせると `pd.to_numeric` が全件 NaN を返し、既定値 0.30 が
全メッシュに乗ったまま **ビルドもテストも成功と表示された**。
負荷スコアの主軸が消えているのに気付けない、最も危険な壊れ方だった。

対策として列名の決め打ちをやめ、`_extract_zoning_codes` が全列を走査して
「用途地域コード(1〜13)として読める列」または「用途地域名として読める列」を
探し、**どちらも無ければ各列の実値を添えて例外にする**ようにした。

判定には罠がある。東京都なら都道府県コードは全件 `13` で、
13 は田園住居地域と同じ値のため有効値の範囲に入ってしまう。
用途地域が 1 種類しかない都市計画区域は現実に無いので、
値の種類数が 3 未満の列は候補から外している。

### 県全体ファイルと市区町村別ファイルの二重計上

A29 東京都の配布物には以下が同梱されている。

    A29-19_13000  都全域 10,684件
    A29-19_13101  千代田区 92件 …（以下 47 市区町村）

全部読むと同じポリゴンを 2 回数え、面積加重平均が壊れる
（同じ場所に用途地域が二重に乗る）。
`read_vector` が「都道府県コード + 000」のファイルを全域版として検出し、
それがあればそれだけを読む。

### 投入結果（渋谷区＋世田谷区）

| 用途地域 | 件数 | 負荷 |
|---|---|---|
| 第一種低層住居専用地域 | 470 | 0.05 |
| 第一種中高層住居専用地域 | 466 | 0.20 |
| 第一種住居地域 | 448 | 0.38 |
| 近隣商業地域 | 428 | 0.74 |
| 商業地域 | 254 | 1.00 |
| 準工業地域 | 161 | 0.78 |
| その他 | 375 | — |

低層住居専用が最多（世田谷の住宅地）、商業地域が渋谷中心部に集中、
工業系はわずか 4 件。対象 2 区の実際の姿と一致しており、
サニティチェックとして機能している。

## 9. 既知の限界

正直に書いておく。

1. **模擬データで動作中。** 実オープンデータを 1 件も取得できていない（README 参照）。
   数値・施設名はすべて架空であり、現時点の出力を提言として引用できない。
2. **`etl/fetch.py` は実サーバに対して未検証。** 列名マッピングは仕様書ベースの想定値。
3. **手帳所持率による区単位の補正は未実装。** `ward_coefficient` 列として
   受け口だけ用意してあり、既定 1.0。
4. **人流データ未組み込み。** 昼間人口メッシュで代替している。
   ODPT チャレンジ経由の民間データは特定利用条件に縛られるため、
   作品の公開範囲と整合するか確認してから入れる。
5. **行政界でのクリップが矩形近似。** 実データでは国土数値情報 N03 の区界に置き換わる。
6. **順位は対象地域内での相対値。** 対象を 2 区から 23 区へ広げれば順位は変わる。
   色は絶対的な危険度ではない。
7. **感覚負荷の実測ではなく代理変数の合成。** 光・匂い・視覚的圧迫感は未評価。
   PLATEAU の 3D 建物データや夜間光による「圧迫感・眩しさ」レイヤーは Phase 2。
8. **ホスト施設が児童館しか入っていない。** 現在の供給側は P14 由来の児童館のみ。
   図書館・区民センター・出張所は公共施設一覧（区市町村オープンデータ）待ちである。
   そのため「半径 700m 以内に転用可能な公共施設が無い」区画の件数は
   **現時点では過大に出る**。画面上部の見出し数値もこの影響を受ける。
   ホスト種別の優先順位（図書館 1 位）も、図書館が 1 件も無いため現在は効いていない。
9. **当事者による検証を経ていない。** スコアが高い場所が実際に退避先を必要とする場所かは、
   当事者団体へのヒアリングで確かめる必要がある。オープンデータだけで完結する設計は
   コールドスタート問題を回避する利点がある一方、この検証を代替しない。
