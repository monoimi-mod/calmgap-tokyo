# プレゼン（2 分）の構成と、提出用キャプチャ

提出フォームの **5-1 スライド（2 分・16:9）** と **5-2 画面キャプチャ（最大 3 枚・
1600×900）**、および **3-8 デモの操作動画（任意・60 秒・無音）** のための台本。

> **数値はビルドごとに動く。** 資料に載せる数字は、**凍らせたビルド 1 つ**から
> 取ること（`docs/status.md` と `python tools/doc_numbers.py`）。
> 本ファイルの数値は 2026-08-06 のビルド。

---

## 0. 方針 — 基準は「何も知らない審査員が 2 分で分かるか」（2026-08-13 に全面改訂）

**主役は方法である。だが 2 分でそれを言葉にすると死ぬ**——ここは変えていない。
変えたのは**順序**である。

### 何を捨てたか

旧構成は `結論 → 根拠を辿る → 重みを変える → 外部照合` だった。
**監査の順序としては正しい。** だが初見の人には効いていなかった:

- **1 枚目が「オープンデータだけで説明可能に算出する方法」で始まっていた。**
  *何の* 場所の話かが決まる前に、方法の話が来る
- **「250m メッシュ 9,507 区画／データ 10 レイヤー（うちスコアに入るのは 8 層）」を
  タイトルに置いていた。** 10 と 8 の対応は外部から
  「8 なの 10 なの、意味が分からない」と言われた箇所である（`CLAUDE.md`）。
  **その 2 つの数を、初見の 1 枚目に置いていた**
- **3 枚目が「優先度 ＝ 需要 × 負荷」。** まだ何が出てくるのかを知らない人に式を出すと、
  「何かを計算する作品」までしか受け取れない
- **4 枚目（重みで変わる・共通 0 件）が、成果より先に来ていた。**
  誠実さの表明が、**成果を見る前だと「答えが出ない道具」に読める**
- **この作品を 1 文で言う「9,507 区画を、人が話し合える十数区画まで絞る道具」が
  7 枚目にあった。** いちばん強い 1 文が、いちばん遅い位置にいた

### 新しい順序

```
問題 → 解決 → 結果 → 根拠 → 信頼性 → どう使われるか
```

**「これは何なのか」を先に決着させ、技術は「しかも辿れる」として後から出す。**
削ってはいない——10 層・8 層・実数と地図の一致・感度分析・外部照合は
全部残っていて、**置き場所だけを後ろへ動かした。**

**疑いは、成果を見せてから立てさせる。** 「では、その順位は信用してよいのか」を
04 の見出しにしてあるのはそのためで、**根拠を先に出すより短い時間で効く。**

**「方法論」という言葉は、やはり一度も使わない。** 視聴者が自分で結論する。

**最後に残すのは作品の正体である**（2026-08-14）。かつて結びは
「9,507 区画を絞る道具です」から始めていたが、**そのあとに使い方の話が続いて
薄まっていた。**「何を作るものではないか」を先に言い切ると、
**「絞り込む道具」のほうが輪郭を持つ**——否定が定義を作る。

### 「どう使われるか」は口に出す。「導入経路」は口に出さない

**別の話である。** 前者は分析の側から言える——**新しい制度も新しい会議も
前提にしていない**ので、「既にある判断の場に出す資料である」までは事実の記述で済む。
後者（誰が何を判断して設置に至るか）は照会も合意も実証もしていない提案で、
**口で足すと根拠の等級が混ざる**（次節）。

**結びの 1 文に「既にある判断の場」を入れてあるのは、初見の審査員が
「で、これは誰がどう使うのか」を最後まで持ち越さないため**である。

## 2. 入れないもの

**2 分に入れると全部が薄くなる。** GitHub にある、と 1 行言うだけにする。

- 列名を中身で同定する仕組み（`require_column`）
- Python / TypeScript の全区画スコア一致検査（`parity_check`）
- selftest 77 件
- 順位化の副作用と絶対尺度への移行
- 固定値 76 個の感度分析

**技術的に最も誇るべき部分だが、2 分では絶対に伝わらない。**

### 駅の話は「事実だけ」口に出す（2026-08-14 に線を引き直した）

**駅は 3 か所に出てくる。口に出すのは事実と 1 句だけである。**

| どこ | 何 | 等級 | 口に出すか |
|---|---|---|---|
| **2 枚目**（12–32 秒） | JR 東日本が横浜駅・立川駅の改札内で実証実験を行った | **事実**（一次情報あり） | **出す** |
| **7 枚目**（結び） | 「都営地下鉄のような駅のバリアフリー施策という既にある判断の場に出せます」 | **事実の記述**（新しい制度を前提にしない範囲） | **1 句だけ出す** |
| **8–9 枚目** | 優先地域 → 候補駅 → 現地確認 → 実証 → 展開 | **提案・政策提案** | **出さない** |

**7 枚目の 1 句で説明を始めないこと。** 2 分の主役は
「9,507 区画から、まず検討すべき場所をデータで絞り込む」ことで、
**駅はその結果が現実の施策へどう接続するかの一例にすぎない。**
ここで導入経路を語り出すと、**結びが提案の話になる。**

**2 枚目の 1 文は課題の側の仕事をしている。** この作品は
「過負荷になるのは移動の途中だ」を前提に需要を組んでいるが、
**それを作者が言うだけでは、ただの想定である。** 鉄道事業者が
実際に駅で試したという一次情報が 1 つあるだけで、
**問題設定が「作者の主張」から「既に事業者が動いている領域」に変わる。**
3 秒で効くので入れる。

**23 区の外であることを必ず添える。** 書かないと「もう解決済み」に読める。

### 導入経路（8–9 枚目）は、口では言わない（2026-08-13）

理由は上の 5 項目と違う。**尺ではなく、根拠の種類が違うからである。**
52–90 秒の 38 秒間は「見つかったもの → 疑う → 根拠を辿る → 全部辿れる」を
画面で実演していて、**この作品の強さはその密度にある。** そこへ
**照会も合意も実証もしていない話**を口で足すと、視聴者の中で
根拠の等級が混ざる——**言ったほうが弱くなる。**

**ただし「既にある判断の場に出せる」の 1 文は結びに残す**（1 節の末尾）。
初見の審査員は「で、これは誰がどう使うのか」を必ず持つので、
**そこを空けたまま終わると、8 枚目を読まない人には答えが無い。**
言えるのは**制度も会議も新設しないと言い切れる範囲まで**で、
その先（誰が何を判断するか）が 8 枚目である。

- 口に出すのは **限界の 1 文**（特別支援学校 1 層への依存）だけにする
- 導入経路は**読む人のための 1 枚**として、**限界の後**（最終ページ）に置く。
  前に置くと、限界が実装の限界に見える
- **「社会実装」という言葉自体を提出物で使わない。**「導入経路」で足りる。
  大きい言葉ほど、根拠の無い話を大きく見せる
- **8 枚目で都営地下鉄を例にしたが、「駅に置くべき」とは言わない。**
  スライドにも「最も筋の通る一例」と書いてある
- **9 枚目（事実／提案／未確認の切り分け）を削らないこと。**
  ここを落とすと、提案と未確認が流れの中で事実の顔をする

**First Stage は収録なので、聞かれた側では答える。**
想定問答は [`implementation.md`](implementation.md) 7 節にある
（当事者検証・想定導入主体・実証の有無・図書館・有料化・特別支援学校依存）。

### 限界は「言わない」のではなく「1 枚に畳む」

15 秒しか無いので、**いちばん重い 1 つだけ**を口に出す:

> 上位の顔ぶれは**特別支援学校というレイヤー 1 枚**でほぼ決まります（外すと上位 10 件が全部入れ替わる）。
> 順位を固定の答えとして読まないでください。

残り（**当事者による検証を経ていない**／多摩未対応／公園データが 2011 年／
混雑が従業者数）はスライドの隅に小さく並べる。**画面には全部書いてある**ので、
「詳しくは画面の『この分析で分からないこと』に」で足りる。

> **「当事者検証が 3 名のみ」と書いてあった（2026-08-07 に訂正）。**
> 検証は**1 度も行っていない**。他の 6 か所——`CLAUDE.md`・`status.md`・
> `methodology.md` 14・`operation-idea.md`・`submission-form.md`・
> **公開中の画面**（`ui.ts` の「この分析で分からないこと」）——はすべて
> 「経ていない」で揃っており、**台本 1 本だけが違うことを言っていた。**
>
> **危ないのは向きである。** 台本は「3 名に見てもらった」と言えと
> 指示していて、実際にしていない。First Stage は収録なので、
> 「その 3 名はどういう方ですか」に答えられない。
> **無いものを有ると言う側の誤りは、限界を書き漏らすより重い。**

## 3. キャプチャ 3 枚（URL で再現できる）

**ディープリンクを入れたので、URL を開くだけで同じ状態になる。**
1600×900 で撮ること（ブラウザの開発者ツール →「スクリーンショットをキャプチャ」が確実）。

| # | 何を見せる | URL |
|---|---|---|
| ① | **結論**（2 枚のカード＋外部照合＋全体地図） | `https://calmgap-tokyo.hiroaki-kuwabara.workers.dev` |
| ② | **根拠が辿れること**（1 区画の内訳・出典・順位） | `…/#c=5339463631` |
| ③ | **148 区画**（一覧が全部「0 件」） | `…/#f=unreachable` |

②の区画は 1 位（江東区 亀戸）。③で先頭に出るのは 新宿区 新宿・西新宿・都庁前。

> **スライドで使う順は ① → ③ → ② である**（3 枚目・4 枚目・5 枚目）。
> **番号は撮った順で、見せる順ではない**——`shoot_captures.mjs` の出力名
> （`01-overview` / `02-evidence` / `03-unreachable`）と対応させてあるので、
> 番号を振り直さない。振り直すと、次に撮り直した人のファイル名と食い違う。

**3 枚とも `docs/captures/` にある。** 撮り直しは 1 コマンド:

```bash
node tools/shoot_captures.mjs
```

### `--virtual-time-budget` で撮ってはいけない（2026-08-07）

**仮想時間で早送りすると、9,507 区画が 1 つも描かれていない画像が出る。**
`#f=unreachable` で踏んだ——ベースマップと右のパネルは正しく写るので、
**縮小して見ると「そういう画面」に見える。** しかも**撮り直すたびに
バイト単位で同じものが出てくる**ので、再実行では気付けない。

原因はアプリ側ではない。同じ URL を普通のブラウザで開けば描かれる。
`requestAnimationFrame` の発火とメッシュのアップロードが仮想時間の
早送りと噛み合わないだけである。**実時間で待つ**ようにした（CDP 経由。
`tools/shoot_captures.mjs`）。

**自動で確かめられるのは「読み込み中でない・順位表が空でない」まで。**
地図ハンドルを外へ出しておらず、canvas も `preserveDrawingBuffer: false`
なので、**メッシュが描かれているかは検査できていない**——
だから撮ったら必ず画像を見る。

## 4. 60 秒の操作動画（任意・無音）

**この作品の見どころは「表の数字と地図の点が一致すること」なので、動画が最も雄弁。**

```
0–10s   全体地図。結論カード 2 枚が見えている
10–25s  順位表の 1 行を押す → 地図が寄る → 根拠と内訳が出る
25–40s  内訳の「障害福祉サービス事業所」を押す
        → 徒歩圏 800m の円が描かれ、44 件が光り、下に 44 行の一覧が開く
        →「表の 44 件・地図の 44 点・一覧の 44 行」が同じであることを見せる
40–50s  スライダーを動かす → 順位表が入れ替わる → 148 の数字も動く
50–60s  「絞り込んで地図に出す」→ 上位が消えて 148 区画が現れる
```

**40–50 秒を入れる理由。** 「重みで動く」ことを画面で見せないと、
**148 が動かない数だと誤解される**（かつて画面がそう書いていた）。

## 5. 使ってはいけない言い回し

過去に撤回した表現。**資料に混ぜないこと。**

| 使わない | 正しくは |
|---|---|
| 「徒歩圏に**退避先**が無い 148 区画」 | 「徒歩圏に**区の公共施設**が無い」——施設があっても設置されているとは限らない |
| 「148 は**重みに依存しない**」 | 重みで動く（プリセットで 133〜171 件） |
| 「屋外に代替の退避先が存在しない」 | 「この区画に緑・公園の被覆がほぼ無い」 |
| 「上位 10 件は◯◯区が…」（過去のビルドの数字） | **必ず凍らせたビルドから取り直す** |
| 「◯◯周辺」という地区名 | 区画単位。区名＋最寄り駅名は**呼び名**であって広がりの主張ではない |
| 「**駅に設置すべき**」「駅が最適解」 | **有力な候補**（本プロジェクトからの提案）。「最も筋の通る一例」であって結論ではない |
| 「JR 東日本と**連携している**」「JR の事例を**踏まえて設計した**」 | **一次情報を引いただけ**。照会も合意もしていないし、設計は先に決まっていた |
| 「JR が駅に**カームダウンスペースを設置した**」 | **実証実験**（2025 年 10〜12 月）で、**パーテーション等の無い「スポット」**。常設ではなく、その後の展開は確認していない |
| 「**都が補助する**」「都の支援制度がある」 | **政策提案**。制度の有無と条件は未確認 |
| 「CalmGap が**駅構内の設置場所を示す**」 | **どの駅・どの地域までが分析**。駅構内のどこかは事業者の現地確認 |

**社会実装について言ってはいけないことは
[`implementation.md`](implementation.md) 5 節に別表がある**（「当事者検証を実施した」
「有料モデルで運営費を賄える」「○○課が導入する」など）。**分けてあるのは
出所を 2 つにしないため**——上の表は分析の言い回し、あちらは実装の言い回しで、
根拠の種類が違う。

## 6. スライドは HTML が原稿で、PDF が提出物（2026-08-07）

```bash
node tools/slides_pdf.mjs      # docs/slides.html → docs/slides.pdf
```

9 枚・16:9（960×540pt）。上の構成表の 7 区間（限界は 6 枚目に畳んである）に、
**口では触れない導入経路の 2 枚**（8 流れ／9 事実と提案の切り分け）を
最終ページとして足した形。
**枚と秒は 1 対 1 で対応する**（2026-08-13 の改訂で揃えた。かつては
6 区間に 7 枚がぶら下がっていて、どの枚をいつ出すのかが表から読めなかった）。

**PPTX にしていない。理由は 2 つある。**

1. **フォントが置き換わらない。** 日本語のスライドは、相手の環境に
   そのフォントが無いと行が折り返して**レイアウトごと崩れる**。しかも
   **作った側の画面では正しく見える**ので、崩れたことに気付けない。
   PDF は字形を埋め込むので、審査員が開いた画面と手元の画面が同じになる
2. **数値が diff に出る。** この作品は「過去の数字を引用しない」を
   機械で守る仕組みを持っている。原稿がテキストなら、そこに載せられる

**数値は検査対象に入れた**（2026-08-07）。`python tools/doc_numbers.py` が
この台本・`slides.html`・`submission-form.md` の 3 本を配信データと
突き合わせる（47 項目）。

**向きが `status.md` と逆である。** `status.md` は「現在値がすべて
書かれていること」を求めるが、**資料は数値の一部しか引かない**——
全部を求めると「区平均の開き 4.0dB がスライドに無い」で落ちる。
だから資料ごとに「載っている値」を明示的に並べてある。
**資料から主張ごと消したときだけ、一覧からも消すこと。**

編集は `docs/slides.html` を直して書き出す。**PDF を直接直さないこと**
（次に書き出した瞬間に消える）。
