# プレゼン（2 分）の台本と、提出用の画面素材

提出フォームの **5-1 スライド（2 分・16:9）**、**5-2 画面キャプチャ（最大 3 枚・
1600×900）**、**3-8 デモの操作動画（任意）** のための台本。

> **数値はビルドごとに動く。** 資料に載せる数字は、**凍らせたビルド 1 つ**から
> 取ること（`docs/status.md` と `python tools/doc_numbers.py`）。

---

## 0. 方針 — スライドは「見るもの」、この文書が「喋るもの」

**基準は「プロジェクトを何も知らない審査員が、2 分の説明だけで
①これは何か ②なぜ価値があるか ③どう実現したか ④どう使うか ⑤何が分かるか
⑥現実にどう使われるか を理解できるか」。**

### 並びを変えた（2026-08-17・ユーザー判断）

**「問題提起 → 方法論 → 結果」ではない。**

```
何を作ったか → なぜ価値があるか → どう実現したか
→ 実際に使う → 条件を変える → 何が分かったか → 社会実装
```

**問題を大げさに語るより、作ったものの価値をスマートに見せる。**
「カームダウンスペースが必要です」から始めるより、
**「東京のどこに設置するとよいのか。それを 9,507 区画から探せる地図を作りました」**
のほうが、この作品そのものの面白さが伝わる。

### 何を直したか

| 直したもの | なぜ |
|---|---|
| **表紙を 1 枚足した** | いきなり説明を始めると、聞き手は「何の話が始まったのか」を探しながら聞くことになる。名前と一行だけ置く |
| **1 枚目を「これは何？」に徹底** | 初見の人はカームダウンスペースを知らない。**絵で 3 段**（街で過負荷 → 落ち着ける場所が必要 → ではどこに設置する？）にし、画面写真を大きく置いた |
| **2 枚目のタイトルを問いに** | 「なぜ置き場所を決められないのか」は初見に意味が通らないうえ、**「決められないから設置されない」という因果をこの作品は証明していない** |
| **「逃げ場が要るのは移動している最中」を落とした** | **比較の主張で、裏が取れない。** 駅の話は 7 枚目に移し、一次情報のある事実だけで組み直した |
| **2 枚目に「絞り込み」の図を大きく置いた** | この作品の値打ちは **9,507 → 上位 50 → 1 区画の根拠**で、それは図でしか短く伝わらない |
| **3 枚目を設計思想 → データの順に** | 「需要 × 負荷」とだけ書くと**なぜそのデータなのか**が分からず、「公開データを集めました」までしか伝わらない |
| **7 枚目を都営地下鉄まで具体化** | 抽象的な「社会実装」より、**誰が何を判断するか想像できる 1 例**のほうが強い |

### さらに直したもの（2026-08-17 その4・ユーザー判断）

| 直したもの | なぜ |
|---|---|
| **全体の文字を大きくした**（本文 12 → 14pt、内訳の見出し 21 → 30pt、図の中の文字も） | **PC で読む資料ではなく、2 分のプレゼンで見せる画面**である。情報を削ってでも読みやすさを採る |
| **1 枚目の見出しを内容に合わせた** | この枚には「設備そのものの説明」と「CalmGap とは何か」の 2 つが入っており、**「カームダウン・クールダウンスペースとは？」だと後半が浮いていた** |
| **4 枚目の左を「使い方」にした** | 見出しが「実際に、こう使う」なのに、左は**動画で何を操作しているかの説明**だった。左＝意思決定の流れ、右＝それを実際の画面で実演、という関係にする |
| **5 枚目の動画にスライダー操作を足した** | プリセットを押すだけだと**「用意された 4 パターンから選ぶ機能」**に見える |
| **6 枚目を地図中心にした** | 148 は**斜線の区画が東京中に散っている絵**そのものが発見である。地図だけを 2 倍解像度で切り出した素材を使う（左パネルごと縮めると 1 区画が 4px になり、斜線があること自体が読めない） |
| **7 枚目の見出しに「社会実装の一例」を入れた** | 導入が決まっている・連携しているように読まれてはいけない |

**基準は「このスライドを 2 秒見ただけで、何が伝わるべきか」。**
情報を減らすことは問題ない。詳細はこの文書に残す。

### 11 枚に組み直した（2026-08-17 その5・ユーザー判断）

**足したのではなく、各枚が何を伝えるために在るのかを整理した。**

| 直したもの | なぜ |
|---|---|
| **表紙のタイトルを 96pt に。画面写真と図を添えた** | 一瞬見て何の作品か分かることを、情報が入りきることより優先する |
| **需要 × 負荷を先に、東京全体の比較を後に** | 「どうやって探すか」が決まってから「その結果どう絞り込めるか」へ渡すほうが自然 |
| **5 枚目を「使用例」に** | 「実際に、こう使う」は**推奨手順**に読める。この道具は目的に応じて自由に使うもので、**必ずこの順で使うものではない**。左は「ある区画で何が確認できるか」の例示にした |
| **6 枚目の見出しを「判断する人の立場によって、優先順位は変わる」に** | 「プリセット A → B で順位が変わりました」は機能紹介にしかならない。伝えたいのは**一つの固定された答えではなく、意思決定の条件を変えて比較できる**という価値 |
| **7 枚目から外部照合を外し、動画にした** | 「外から確かめました」「中央値 4,765 位」は、初見の人には**「それで何が分かったの？」**になる。本筋は「分析すると検討すべき場所が見えてくる」ことなので、**「絞り込んで地図に出す」で斜線が浮かび上がる動画**に替えた |
| **8 枚目を社会実装の中心に作り直した** | なぜ都営地下鉄か → 導入の流れ（6 段）→ どの重み設定でも残る駅、の 3 段。**CalmGap が担うのは候補を絞るところまで**を明示 |
| **9 枚目（今後の課題と展望）を足した** | 機能一覧にしない。課題は 3 つの束に畳み、**展望は 1 行**。この作品を作った動機がいちばん伝わる枚 |
| **10 枚目（技術スタック）を足した** | 技術自慢にしない。**公開データ → 空間分析 → 地図・UI → 公開**の流れが見えれば足りる |
| **11 枚目から「当事者による検証は経ていません」を外した** | 参考文献のページを**「できていないこと一覧」**にする必要はない。実証と当事者評価は 9 枚目の課題として扱う |

**「基準がバラバラ」「同じ地図を持っていない」のような抽象表現は使わない。**

### 分担

| | |
|---|---|
| **スライド** | 短いタイトル・大きな数字・図・画面・**動画**・最小限の補足だけ |

**「方法論」という言葉は一度も使わない。** 視聴者が自分で結論する。

### 一本のストーリーとして読む

**接続詞で繋ぐ。** 枚ごとに独立した説明を並べると、聞いている側は
**毎回「いまどこの話か」を組み立て直す**ことになる。

```
（何の場所か）→ では、どこに置けばいいのか
→ まず、需要 × 負荷で決めた   → そのうえで、9,507 区画を比べる
→ たとえば 2 位を開くと…      → ただし、唯一の正解は出さない
→ そして、見えてきたのが 148  → では、これをどう使うか
→ 最後に、何がしたいのか
```

### 尺は実測で決めてある（2026-08-17 その6）

**読み上げて 2 分 40 秒かかった**（ユーザー実測）。1,034 字を 160 秒なので **6.5 字/秒**。
1 度詰めて 715 字（1 分 50 秒）にしたが、**その速さがそもそも早口で不自然**だった。

**速さのほうを基準にし直した。**

| 速さ | 何 | 596 字だと |
|---|---|---|
| **5.5 字/秒** | ニュース読みくらい。**この台本の想定** | **1 分 48 秒** |
| 6.0 字/秒 | やや速い | 1 分 39 秒 |
| 6.5 字/秒 | **実測。早口で不自然だった速さ** | 1 分 32 秒 |

**1,034 → 596 字**（42% 減）。**自然な速さで 2 分に収まり、余裕が 12 秒ある。**

### 何を削ったか

**削ったのは説明であって、事実ではない。** 落とした内容は文書の他の節にある。

| 落としたもの | どこに在るか |
|---|---|
| 需要・負荷の 8 層の名前 | **3 枚目のスライドに全部出ている** |
| 既存 11 か所の外部照合 | 下の「スライドから外して、ここに残した数値」 |
| 「分析すると検討すべき場所が見えてくる」 | **7 枚目のタイトルがそう書いてある** |
| 「絞り込むと東京中に浮かび上がります」 | **動画がそれを見せている** |
| 「表の件数と地図の点と一覧の行数が一致」 | 5 枚目のキャプションにある。口では「最後まで辿れます」まで |
| 「東京都自身の事業者です」 | 8 枚目の箇条書きにある |

**規則を 2 つ立てた。**

> **スライドに書いてあることを読み上げない。** タイトルと大きな数字は見れば分かる。
> 口では**画面に書いていないこと**だけを言う。
>
> **動画が見せているものを言葉でなぞらない。** 見ている側は画面を追っているので、
> **同じことを言うと二重になる。** 動画の区間は**言葉を減らすほうが伝わる。**

**動画の尺が下限になる。** 5〜7 枚目は動画（17 / 16 / 9 秒）が回りきる時間が要るので、
**その区間は短くしても待つ**。**沈黙は事故ではない**——実演を見せている時間である。

## 2. 入れないもの

**2 分に入れると全部が薄くなる。** GitHub にある、と 1 行言うだけにする。

- 列名を中身で同定する仕組み（`require_column`）
- Python / TypeScript の全区画スコア一致検査（`parity_check`）
- selftest 77 件
- 順位化の副作用と絶対尺度への移行
- 固定値 76 個の感度分析

**技術的に最も誇るべき部分だが、2 分では絶対に伝わらない。**
**4・5 枚目の動画が代わりに仕事をする**（表と地図と一覧が一致することは、
説明されるより見たほうが速い）。

### 駅の話は 7 枚目にまとめ、一次情報だけで組む（2026-08-17）

**「逃げ場が要るのは移動している最中」を捨てた。** この作品は移動中と滞在中を
比べていないし、一次情報にもその比較は無い。**比較の主張は使わない。**

**代わりに使えるのは、交通結節点への設置が実務として積み上がっているという事実**

## 3. 操作動画 3 本（スライドに埋め込む）

**この作品の見どころは「表の数字と地図の点が一致すること」なので、動画が最も雄弁。**
文章にすると 3 行になるものが、動くと 20 秒で伝わる。

```bash
node tools/shoot_demo.mjs               # 3 本とも docs/demo/ へ
node tools/shoot_demo.mjs unreachable   # 1 本だけ
```

> **`CALMGAP_SITE` で撮る先を差し替えられる。** 既定は公開中のサイトで、
> **撮るものと審査員が見るものを同じにする**ため。差し替えは
> **回線が落ちて公開サイトから撮れないときの逃げ道**である
> （2026-08-17 に実際に踏んだ。`mesh.geojson` 7.5MB が 11KB/s まで落ち、
> 20 秒でも読み込みが終わらなかった）。**使ったときは記録に残すこと。**

**撮るのは公開中のサイトそのもの**で、押す場所を CSS セレクタで指すだけである。
画面の中身をツールに書いていないので、**UI が変われば撮り直しが落ちる。**

### ① `demo-evidence.mp4`（約 17 秒・5 枚目）

```
初期画面
→ 提言リストの 2 位を押す        → 地図が寄り、根拠と内訳が出る
→ 需要側の内訳まで送る
→「障害福祉サービス事業所」を押す  → 徒歩圏 800m の 58 件が地図で光る
→ 一覧まで送る
→ 一覧の 1 件を押す              → 地図の吹き出しに施設の詳細
```

**順位が出る → なぜその順位なのか分かる → 根拠となった施設が地図で確認できる
→ その施設の詳細まで確認できる。** この 4 段を、説明ではなく実演で見せる。

### ② `demo-weights.mp4`（約 16 秒・6 枚目）

```
重みプリセットまで送る
→「通所先・通学先の近く」を押す   → 順位表が入れ替わる
→ スライダーまで送る
→ 駅乗降規模のつまみを上げる      → 順位表も地図の色も、さらに変わる
```

**伝えたいことは 1 つだけ。重みを変えると、優先順位も変わる。**

### ③ `demo-unreachable.mp4`（約 9 秒・7 枚目）

```
初期画面（東京全体の優先度）
→「絞り込んで地図に出す」を押す  → 順位表が 148 区画だけになり（公共施設は全部 0 件）、
                                  地図に斜線の区画が浮かび上がる
```

**この機能は既に画面にある。** 新しく作ったものではなく、
**分析すると検討すべき場所が見えてくる**ことを実演で見せるために使う。

**プリセットを押すだけで終わらせない**（2026-08-17 その4・ユーザー判断）。
それだと**「あらかじめ用意された 4 パターンから選ぶ機能」**に見える。
**つまみを自分で動かせる**ところまで見せて、初めて
「利用者自身が何を重視するかを調整できる」が伝わる。

> **つまみが動かない収録が撮れた。** `Input.dispatchMouseEvent` の移動側に
> `button: "left"` を付けていなかったため、Chrome の range 入力が
> **押した瞬間の値のまま止まった**（0.9 → 0.3 になってそこから動かない）。
> **収録は最後まで走り、成功と表示される。**
> いまは撮ったあとに値を読み直して、指定した位置に無ければ止める。

### カーソルは描いている

ヘッドレスの画面にマウスポインタは写らない。**何も押していないのに画面が変わる動画**は
実演として読めないので、`Input.dispatchMouseEvent` を送る座標と**同じ座標**に印を描いている。
座標の出所は 1 つなので、**印と実際のクリックが食い違うことは無い。**

### 動画の中身は機械で検査できない

だから**キャプションの数値がその代わりをしている**（`tools/doc_numbers.py` が
2 位の区画の実数を照合する）。**落ちたら、数字を書き換えるのではなく動画を撮り直すこと。**
数字だけ直すと、動画と資料が別の区画を指す。

### `--virtual-time-budget` で撮ってはいけない（2026-08-07）

## 6. スライドは HTML が原稿。提出物は PPTX と PDF（2026-08-17）

```bash
node tools/shoot_demo.mjs      # 先に動画を撮る（4・5 枚目が参照する）
node tools/slides_pptx.mjs     # docs/slides.html → docs/slides.pptx（動画が再生される）
node tools/slides_pdf.mjs      # docs/slides.html → docs/slides.pdf （静止画）
```

**11 枚・16:9（表紙 1 ＋ 本編 8 ＋ 技術 1 ＋ 出典 1）。5-1 に出すのは PPTX のほうである。**

### なぜ PPTX にしたのか。フォントは崩れないのか

**PDF は動画を再生できない。** この作品の強さは操作にあるので、
**動画が再生される側**を主の提出物にする。

**PPTX を避けてきた理由は消えている。** 「日本語のフォントが相手の環境に無いと
行が折り返してレイアウトごと崩れ、しかも作った側の画面では正しく見えるので
気付けない」が理由だったが、**この書き出しは各ページを HTML から焼いた画像 1 枚**で、
**PPTX 側にテキストボックスが 1 つも無い。置き換わるフォントが存在しない。**

代わりに失うのは**文字の検索と選択**なので、**PDF も併せて書き出しておく。**

**動画の位置はスライドの HTML が決める**（`[data-video]` が付いた要素の矩形）。
座標を 2 か所に持つと、レイアウトを直したときに片方だけ古くなる。
その要素のポスター画像がそのまま PowerPoint の表紙になるので、
**PDF に写っているコマと、PPTX の再生前に見えるコマが同じもの**になる。

**PDF も PPTX も直接直さないこと**（次に書き出した瞬間に消える）。

### 数値は検査対象に入っている

`python tools/doc_numbers.py` がこの台本・`slides.html`・`submission-form.md` の
3 本を配信データと突き合わせる。

**向きが `status.md` と逆である。** `status.md` は「現在値がすべて
書かれていること」を求めるが、**資料は数値の一部しか引かない**——
全部を求めると「区平均の開き 4.0dB がスライドに無い」で落ちる。
だから資料ごとに「載っている値」を明示的に並べてある。
**資料から主張ごと消したときだけ、一覧からも消すこと。**
